# Story Editor large-story performance and equivalence plan

**Baseline:** main `f9e8f2f` (2026-11-20). Read root `AGENTS.md`, `editor/qa/README.md`, package READMEs/AGENTS, and `docs/FORMAT-COMPARISON.md` before work.

## Goal

Find whether the checker, map, autosave, export, or player build is the first material bottleneck for a large but valid synthetic story. Keep the editor as the single source of truth. Generated package code remains generated by `npm run build`; tests compare packages with the editor and must continue to do so. Use original generated stories only; do not include real people’s stories or private content.

## Workload and permutation matrix

Generate deterministic stories at 10, 100, 1,000, and 5,000 pages, then increase only while the browser remains stable. Cross page count with 1/3/8 choices per page; short and long labels; shallow and deep branching; reachable and unreachable endings; item/number/dice rules; cross-links; and repeated subgraphs. Record story bytes, branch count, rule-state count, and map edge count. Keep the random seed in every result.

Measure separately: parse/validate, check tab analysis, map layout, pan/zoom and redraw, autosave serialization, native export, Twine import on a bounded archive, package generation, and exported-game first interaction. Do not include story generation or browser startup in timed regions. Compare cold open, warm redraw, one edit, undo/redo, and full rebuild. Test at 320, 390, 768 and 1280 CSS px; desktop and phone input are separate.

## Correctness gates

For each fixture, compare editor, package and exported-game answers using the existing contract tests and a small independent oracle. Preserve author text exactly, including the empty-author case. Keep missing pages, impossible conditions, malformed imports, duplicate identifiers, huge pasted text, and corrupted saves on the safety path. A performance result must not change checker conclusions, map semantics, generated game behavior, offline operation, or accessible announcements.

Use the existing staged runner: `node editor/qa/qa.js sample` while iterating, `quick` for the project’s common regressions, and `full` on Firefox, Chromium and WebKitGTK at final qualification. Use `--against` for any new bug regression. Record WebKit’s documented window/touch limitations and report them rather than treating stand-ins as native touch. First identify which existing tier actually covers each changed file; do not run all suites for a docs-only proposal.

No worker conversion, data structure rewrite, persistence change, dependency, or public package API is authorized by this plan. If a hot path needs a worker, make transfer, cancellation, error, and fallback behavior a separate candidate and preserve the main-thread result as the oracle.
